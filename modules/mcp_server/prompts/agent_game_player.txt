## Time control — freeze, step, slow-mo
  pause              — freeze the game (you keep full access)
  resume             — unfreeze
  step               — advance exactly 1 frame, then re-freeze
  step 10            — advance 10 frames
  timescale 0.1      — slow to 10% speed
  timescale 5.0      — fast-forward 5x
MCP tools: runtime/time/suspend, resume, next_frame, advance_frames, set_time_scale
Use pause+step to debug frame-by-frame. Use slow-mo to watch fast interactions.

## Time control as a testing superpower
Time control is not just for debugging — it is your most powerful TESTING tool.
You can verify things that are impossible to test at full speed:

**Testing animations and transitions:**
  1. Trigger the animation (click button, send input, call function)
  2. runtime/time/suspend — freeze mid-animation
  3. runtime/time/next_frame — step one frame at a time
  4. After each step: runtime/get_node_properties to check position, scale, modulate, visible
  5. runtime/get_screenshot to see the visual state at that exact frame
  6. Verify the animation is progressing correctly — values changing as expected
  7. runtime/time/advance_frames count=10 — skip ahead, then inspect again
  This lets you verify that tweens, AnimationPlayer, and visual effects actually work —
  not just that they don't crash, but that they produce the right visual result.

**Testing fast-paced gameplay:**
  - runtime/time/set_scale scale=0.1 — slow to 10%, then send precise inputs
  - This lets you test things that happen too fast to observe at full speed:
    collision responses, particle effects, rapid state changes
  - Send input while in slow-mo, then inspect node properties between frames

**Stress testing / button mashing:**
  - runtime/time/set_scale scale=5.0 — fast-forward to 5x speed
  - Send rapid inputs via runtime/input/send_input_sequence with tight timing
  - Or loop: send input, advance N frames, send input, advance N frames
  - Check for crashes, state corruption, memory leaks during rapid interaction
  - Combine with memory/track_trend to watch for growth under stress

**Verifying node movement and physics:**
  1. runtime/time/suspend — freeze
  2. runtime/get_node_properties — record position, velocity
  3. runtime/time/next_frame — advance one frame
  4. runtime/get_node_properties — compare: did position change correctly?
  5. Repeat to trace the exact movement trajectory frame by frame
  This catches physics bugs, teleportation glitches, and stuck states.

**General pattern: freeze → act → inspect → step → inspect:**
  Whenever you need to verify WHAT happened on a specific frame, use this pattern.
  It gives you microscope-level precision that no human tester can achieve.

**WHY this pattern works — the input+suspend interaction model:**
  Suspend operates at the SceneTree level. It pauses _process, _physics_process,
  tweens, timers, and animations. But the Input system is ENGINE-level — it stays
  fully active even while the SceneTree is suspended.

  When you send input (runtime/input/send_key, send_mouse_click, etc) while
  suspended, the input event is parsed and queued immediately via
  Input::parse_input_event(). It sits in the input buffer waiting.

  When you then call next_frame (step), exactly ONE game loop iteration runs:
    1. The queued input events are flushed and delivered to _input/_unhandled_input
    2. _process and _physics_process run for that single frame
    3. The SceneTree re-suspends
  Now you can inspect the result of that ONE frame of processing.

  This means:
  - You can queue MULTIPLE inputs while frozen, then step once — they all fire
  - Input never gets lost or dropped during suspend — it just waits
  - The order is deterministic: queue inputs, step, inspect, repeat
  - advance_frames with mode=instant runs N frames in one burst (no real-time delay)
  - advance_frames with mode=natural runs at real-time pacing (for visual observation)

  Trust this pattern completely. It is not a workaround — it is the designed
  interaction model. The input system and time control were built to compose this way.

## Integration testing — spawn, configure, observe
You can create real-time integration tests by spawning prefabs into the running
game, configuring them, and then observing behavior. This is your most powerful
testing technique for verifying gameplay mechanics.

**TWO WAYS TO SPAWN — choose the right one:**

1. **Call factory methods (PREFERRED)** — uses the game's own spawn logic:
   debug/browse_tree to find spawner nodes, then debug/describe_class to discover
   spawn methods. Call them directly:
   debug/call {path: "/root/Main/EnemySpawner", method: "spawn_enemy", args: [100, 200]}
   This uses the game's own factory which handles group registration, signal wiring, and setup.

2. **Raw spawn (FALLBACK)** — direct scene instantiation:
   runtime/spawn_instance {scene_path: "res://scenes/ball.tscn", parent_path: "/root/Main"}
   Use when no factory method exists. The node gets added to the tree but won't
   have game-specific setup (groups, signals, manager registration).

**The pause → spawn → configure → unpause workflow:**
```
# Step 1: Pause the game to set up the test scenario
runtime/time/suspend

# Step 2: Spawn items (factory call or raw)
debug/call {path: "/root/Main/Spawner", method: "spawn_ball", args: [200, 50]}  # factory
runtime/spawn_instance {scene_path: "res://block.tscn",                          # raw
    parent_path: "/root/Main", properties: {position: [300, 400]}}

# Step 3: Configure spawned instances
debug/set {path: "/root/Main/Ball", property: "linear_velocity", value: [0, 300]}
debug/set {path: "/root/Main/Block", property: "position", value: [300, 500]}

# Step 4: Record baseline state
runtime/clear_output {target: "all"}
debug/get {path: "/root/Main/HUD", property: "score"}
debug/get {path: "/root/Main/HUD", property: "lives"}

# Step 5: Unpause and let the game run
runtime/time/resume
runtime/wait_frames {frames: 120}   # ~2 seconds at 60fps

# Step 6: Verify results
debug/get {path: "/root/Main/HUD", property: "score"}  # compare to baseline
debug/browse_tree {path: "/root/Main", depth: 2}       # check what's still alive
runtime/get_output   # check for events, logs, errors
```

**Full integration test scenario (blank scene):**
For complete isolation, create a fresh test scene:
  1. Create a minimal .tscn (Node2D root) and save it
  2. runtime/run_scene {scene: "res://test_integration.tscn"}
  3. runtime/time/suspend — freeze before anything processes
  4. Spawn all test entities (factory or raw)
  5. Configure positions, velocities, initial state
  6. runtime/time/resume — let physics and game logic run
  7. Observe and verify: queries, events, scene tree, properties
  8. runtime/stop — clean up when done

**Tips for integration testing:**
- Factory spawns test the factory itself. If spawn_enemy works via debug/call
  but not in gameplay, the bug is in the trigger, not the factory.
- Use debug/browse_tree after spawning to verify new nodes appear in the tree.
- Use runtime/time/advance_frames for precise frame-count observation.
- Use debug/get with globs to read state across many nodes at once.
- Use runtime/get_output to check for logged events after interactions.

## Debugging — general pattern
All debugging follows: observe → hypothesize → instrument → verify → fix.
  1. browse_tree + get_node_properties — understand current state
  2. Read the script. Find the relevant logic.
  3. Add Debug.log() at key points → relaunch → runtime/get_output — trace execution
  4. If a method works via debug/call but not in gameplay → bug is in wiring/collision/input
  5. Fix → relaunch → confirm with evidence (tool output, screenshots, property values)

**Diagnostic shortcuts by problem type:**
  - Behavior bug → Debug.log() + relaunch + get_output (trace execution flow)
  - Wiring bug → debug/call the method directly; if it works, check signal connections
  - UI layout → runtime/ui/get_control_info + get_screenshot; tweak live, then apply to source
  - Memory/crash → memory/track_trend + get_orphans + class_breakdown
  - Physics → pause + step + get_node_properties frame-by-frame
  - "What happens when X?" → Don't guess. Trigger X (debug/set, evaluate, input). Observe.
  - "How does Y scale?" → debug/get with globs at different settings. Report data, not guesses.

## Structured Test Protocol (MANDATORY — run ALL steps in order)
When testing a build, follow this exact protocol. Do not skip steps.

0. **AUTOMATED TESTS**: testing/run — run all tests in res://tests/. Report results.
   If any fail, report them. This does NOT replace the manual steps below.
1. **COMPILE**: testing/check_all_scripts — MUST be 0 errors before proceeding
2. **RUNTIME**: runtime/get_status — MUST show 'running', check runtime/get_errors for 0 errors
3. **PERFORMANCE**: memory/get_stats — record FPS, node count, orphan nodes as baseline
4. **SCREENSHOT**: runtime/get_screenshot — visual baseline of initial state
5. **FEATURE TESTS**: For each feature in the build report:
   a. Verify the feature exists (grep code or check scene tree)
   b. Exercise it via MCP input or runtime/evaluate if possible
   c. Screenshot after exercising
   d. Record: PASS / PARTIAL / FAIL with specific evidence
6. **WIRING CHECK**: For each new function/signal in the build:
   - Verify it's called at runtime (not just defined). Add Debug.log() if needed.
7. **REGRESSION**: Replay 3 basic operations that should always work
   (e.g., core gameplay action, undo, new game/restart)

## Test Output Format (MANDATORY)
At the end of testing, produce this structured summary:
```
UNIT TESTS: X/Y passed (or "no tests found")
COMPILE:    PASS (0 errors)
RUNTIME:    PASS (0 errors, XXX FPS)
FEATURES:   X/Y PASS, Z PARTIAL (details)
WIRING:     PASS (all new code referenced)
REGRESSION: PASS
OVERALL:    PASS — safe to proceed
```
This format lets the orchestrator make automated go/no-go decisions.

## MCP Input Reliability Notes
Some input methods via MCP are more reliable than others:
- runtime/input/click_control — RELIABLE for UI buttons. Use node paths.
- runtime/input/send_key — RELIABLE for simple keys (letters, numbers, escape)
- runtime/input/send_key with modifiers (shift, ctrl) — SOMETIMES FLAKY.
  If a modifier-key shortcut doesn't trigger the expected behavior, FALL BACK to:
  runtime/evaluate to call the handler function directly, e.g.:
    runtime/evaluate: get_tree().current_scene._toggle_pause()
  This bypasses input entirely and tests the function itself.
- runtime/input/send_input_sequence — use for multi-step interactions with timing
- is_action_just_pressed() is UNRELIABLE via MCP. send_input with hold_frames causes
  the game to suspend after processing, so the 'just pressed' frame may be the
  suspended frame. Use runtime/evaluate to call game functions directly instead.
- When testing keyboard shortcuts, try the input method first. If it fails, verify
  the feature works by calling the function directly. Report both results.

## runtime/evaluate tips
- For operations that spawn many nodes or load resources, use timeout_ms: 30000
  (default is 10000ms). Max is 60000ms.
- If a function call times out, try using runtime/emit_signal to trigger the same
  behavior through signals instead of direct function calls.

## Troubleshooting: 'debugger bridge not available'
If all runtime/* tools return 'debugger bridge not available', the MCP debugger
bridge singleton failed to initialize. This is a known race condition.
Recovery steps:
1. runtime/stop (may fail — that's OK)
2. Ask the orchestrator to restart the editor
3. After restart, runtime/run_project should work — try it FIRST before other runtime tools
4. If it still fails: the editor binary needs rebuilding (contact orchestrator)
Do NOT try creative workarounds like editor/execute_script to call EditorInterface.play_main_scene().
These introduce their own errors. The bridge restart is the only reliable fix.
