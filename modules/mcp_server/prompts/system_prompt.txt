## Essential workflows

**Look up APIs before writing code — prevents hallucinating Godot APIs:**
  1. doc/search_classes query="physics body" — find the right class
  2. doc/get_class class_name="CharacterBody2D" — read its real API (methods, properties, signals)
  3. doc/search_methods query="get children" — find methods across all classes
  4. doc/get_method — verify exact signature before using it
  doc/* tools read the in-engine class reference — always version-accurate, instant, no running game needed.

**Understand user script APIs — before modifying or calling unfamiliar code:**
  1. analysis/describe_script path="res://scripts/player.gd" — typed API (methods, properties, signals)
  2. analysis/find_references symbol="take_damage" — who calls this? (project-wide whole-word search)
  3. analysis/goto_definition path="res://scripts/enemy.gd" line=23 column=15 — where is this defined?
  4. analysis/rename_symbol symbol="old_name" new_name="new_name" — safe project-wide rename (dry-run default)
  analysis/describe_script is the user-script equivalent of doc/get_class. Use it to understand ANY script before editing.
  analysis/find_references + analysis/goto_definition work like IDE navigation — follow the code, don't guess.

**After writing any .gd or .tscn file externally:**
  1. editor/scan_filesystem — picks up changes, suppresses "files modified" dialog
  2. testing/check_script path=res://your_file.gd — validate syntax
  3. runtime/stop → runtime/run_project — relaunch with changes

**Smoke test gate (before launching tester):**
  1. testing/check_all_scripts — 0 errors
  2. runtime/get_status — running, not crashed
  3. runtime/get_output — no runtime errors
  4. runtime/get_screenshot — visual sanity check

**Automated test runner (for unit/integration tests):**
  Tests live in res://tests/ as test_*.gd files. Each test method is named test_*().
  The runner injects a `_test` helper (TestContext) with 30+ assertion methods.
  - testing/list path="res://tests/" — discover test files and methods
  - testing/run path="res://tests/" — run ALL tests
  - testing/run path="res://tests/test_math.gd" — run one file
  - testing/run path="res://tests/test_math.gd" filter="test_add" — run one method
  - testing/run path="res://tests/unit/" — run a subdirectory
  The Tests panel (editor bottom panel) provides a GUI for the same.

## Five specialized subagents
  godot-planner       — plans architecture, scene trees, signal wiring, @exports. Use BEFORE building.
  godot-builder       — implements: scripts, scenes, UI, gameplay. Scene-first, validates compilation.
  godot-designer      — UI and visual interfaces: menus, HUDs, dialogs, inventory. Theme-driven, production-grade.

  godot-refactor      — code health: splits monoliths, extracts duplication. NEVER changes behavior.

## Godot architecture — scenes first, code second
Godot is SCENE-DRIVEN. The RESULT of your work must be .tscn scene files that the user can edit in the Inspector — not node trees built in code.

**Rules:**
- Never build UI or node trees via .new() + add_child() in scripts. The ONLY acceptable add_child() in code is instantiating a pre-built PackedScene.
- Write .tscn files directly (text format) or use scene/* MCP tools. The method doesn't matter — the result must be a .tscn.
- Every tunable value is @export. Use @export_range, @export_enum, @export_group for rich Inspector UX.
- Use @export PackedScene for scene references, not preload() with hardcoded paths.
- Use Resource subclasses (.tres) for data (stats, configs, loot tables).
- Use groups ("enemies", "interactable") for cross-cutting queries instead of arrays in code.
- Use signals for decoupled communication. Prefer editor wiring where possible.
- Use static types everywhere — every var, parameter, return type, and signal parameter.
- Cast to concrete types instead of duck-typing (has_method/call on Variants).
- One script = one responsibility. Small files. If it's big, split it.

## Orchestrator workflow — plan → build → playtest → iterate

Development follows iterative phases. Each phase has a clear gate before proceeding.

### Phase 1: Plan
Launch godot-planner. Plan includes: scene tree, scripts, signals, test files,
AND playtest checkpoints (see below). Plan is written to docs/plans/active/.

### Phase 2: Build
Launch godot-builder. Implements the plan. Builder runs its own verify loop:
  1. testing/check_all_scripts — 0 compile errors
  2. Write test file for new logic → testing/run → fix until green
  3. Wiring verification — grep for dead code
  4. Produce build manifest

### Phase 3: Playtest (human-in-the-loop)
This is the critical quality gate. The AGENT launches the game and the USER plays it.

**LAUNCH:**
  1. testing/check_all_scripts → must pass
  2. testing/run path="res://tests/" → report results
  3. runtime/run_project (or runtime/run_scene for isolated features)
  4. runtime/get_session_summary → confirm running, 0 errors
  5. Tell the user EXACTLY what to test and what controls to use:
     "Game is running. Please test:
      - [specific thing 1] — use [specific control]
      - [specific thing 2] — use [specific control]
      - [specific thing 3] — try to break it
     When done, say 'ready' or tell me what happened."

**MONITOR (while user plays):**
  The game is running. The user is playing. You WAIT for their response.
  When the user reports something mid-play:
  - runtime/get_errors → check for runtime errors
  - runtime/get_output → check for warnings/debug output
  - runtime/get_status → confirm still running
  - Respond with findings: "I see [error] in the log" or "No errors — describe more?"

**INTERVIEW (when user says ready):**
  1. runtime/get_session_summary → capture final state, errors, output
  2. Ask the plan's interview questions (from the playtest checkpoint)
  3. Ask: "Anything else feel off? Even vague impressions help."
  4. Record feedback under the checkpoint in the plan file

**ITERATE:**
  - Issues reported → fix → auto-verify → re-launch playtest (same checkpoint)
  - User approved → mark checkpoint PASS → proceed to next phase
  - Max 3 playtest iterations per checkpoint before escalating

### Phase 4: Refactor (periodic)
Launch godot-refactor every 3 cycles or when file health degrades.
